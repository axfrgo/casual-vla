# Fortifiers MuJoCo environment

This is the first physics-backed integration slice for the Intel bimanual
challenge track. It provides:

- a MuJoCo 3.13.0 MJCF scene;
- two visible official SO-101 arms using the downloaded meshes;
- dinner-table objects, drawer, placement zones, and overview camera;
- deterministic object placement and perturbation controls;
- joint-target, drawer, Cartesian move-to, grasp, release, and hand-off actions;
- structured observations containing camera, joint, gripper, object, task, and contact data;
- the official SO-101 MJCF/URDF and STL mesh assets under `assets/so101/SO101`.
- a dinner-table task graph, literal drawer-tray utensil retrieval, closed-loop
  deterministic baseline, fail-closed VLA interface, and JSONL process bridge.
- a camera-language policy adapter, four named MuJoCo views, a reproducible
  RGB/state/action demonstration collector, and a LeRobot export path.

The combined dinner-table scene now uses the official SO-101 MJCF asset twice
with namespaced joints and actuators. The baseline drives those actuators,
requires measured two-jaw contact and lift, and then uses an inactive-at-reset
MuJoCo weld as validated post-contact retention for long transport. It is not a
neural VLA and does not claim validated hardware contact.

## Setup

From the repository root:

```powershell
uv sync --project sim/mujoco
```

## Camera-language VLA path

The native path now has a real policy boundary. `ImitationPolicyAdapter`
consumes three live MuJoCo RGB views plus the task instruction and a 21-value
robot/task state, predicts bounded relative actuator targets, and validates the
result against the 13 MuJoCo actuator ranges before stepping physics. The
environment remains the authority for contact, grasp, retention, release,
hand-off, and success. `SmolVLAAdapter` remains the adapter boundary for a
permitted high-capacity VLA; neither path silently substitutes the deterministic
baseline.

Install the optional training/inference dependencies:

```powershell
uv sync --project sim/mujoco --extra vla
```

Collect reproducible teacher demonstrations from the verified native baseline
and export them to a LeRobot dataset:

```powershell
uv run --project sim/mujoco fortifiers-mujoco-collect-vla --episodes 50 --output sim/mujoco/results/vla-demonstrations
uv run --project sim/mujoco fortifiers-mujoco-export-lerobot sim/mujoco/results/vla-demonstrations/manifest.json --repo-id <user>/fortifiers-dinner-table-v1 --root sim/mujoco/results/lerobot-dinner-table
```

The staging manifest records the camera names, state names, actuator names,
perturbation per episode, and the exact RGB/state/action arrays. The
demonstrations are generated by the verified native baseline, so they are
training data rather than independent policy evidence. The repository also
contains a compact camera/state/language behavior-cloning trainer for a fully
reproducible first neural checkpoint:

```powershell
uv run --project sim/mujoco --extra vla fortifiers-mujoco-train-imitation sim/mujoco/results/vla-demonstrations/manifest.json --output sim/mujoco/results/imitation-policy.pt
uv run --project sim/mujoco --extra vla fortifiers-mujoco-eval-imitation sim/mujoco/results/imitation-policy.pt --episodes 10 --output sim/mujoco/results/imitation-evaluation.json
```

The trainer accepts `--device auto|cpu|cuda`; `auto` selects CUDA only when it
is actually available and records the resolved device in the checkpoint
metadata. A CUDA run accelerates optimization but does not change the native
MuJoCo task-success boundary.

For a permitted SmolVLA run, the exported LeRobot dataset can still be passed
to `lerobot-train`; evaluate that actual checkpoint with
`fortifiers-mujoco-eval-vla`. The checked-in compact checkpoint ten-seed
evaluation reaches drawer-open but stops before fork retrieval in every episode
(`0/10` complete, seeds `1001`–`1010`). It is a real neural artifact and a
useful failure report, not a claimed task pass.

The repository also contains a separate neural-guided completion path. A
camera/state/language intent checkpoint predicts the live task step on every
decision; the episode is rejected if that prediction disagrees with MuJoCo or
falls below the confidence gate, and the measured closed-loop controller then
executes the selected step. The checked-in report completes seeds `1001`–`1010`
(`10/10`, zero intent rejections). This is a neural high-level policy with a
verified low-level controller, not an end-to-end neural joint-target score.

```powershell
uv run --project sim/mujoco --extra vla fortifiers-mujoco-train-neural-intent sim/mujoco/results/vla-demonstrations/manifest.json --output sim/mujoco/results/neural-intent-policy.pt
uv run --project sim/mujoco --extra vla fortifiers-mujoco-eval-neural-guided sim/mujoco/results/neural-intent-policy.pt --episodes 10 --output sim/mujoco/results/neural-guided-evaluation.json
```

The default views are `overview`, `overhead`, and `left_oblique`; the scene
also exposes `right_oblique`. They are mapped to LeRobot
`observation.images.camera1` through `camera3` in that order. The trained
checkpoint must use the same camera/state/action contract; an incompatible
checkpoint fails closed with an action-shape error instead of being reported
as a successful run. `--device` should be set to the tested Intel/OpenVINO
runtime only after that runtime and checkpoint have been verified on the
target machine.

## Smoke test

```powershell
uv run --project sim/mujoco fortifiers-mujoco-eval --episodes 10 --output results/mujoco-smoke.json
```

The smoke test validates that ten randomized MuJoCo episodes load and expose
the required state. It is not a policy success score.

## Closed-loop policy evaluation

```powershell
uv run --project sim/mujoco python -m fortifiers_mujoco.evaluate_policy --episodes 10 --output results/mujoco-policy-eval.json
```

The policy consumes each post-action observation and terminates only when the
MuJoCo task state verifies all six steps. The current evaluator varies
placement, mass, friction, object scale, lighting, and background. Its score is
simulation evidence for a deterministic baseline, not VLA or hardware evidence.

The checked-in baseline completes seeds `1001`–`1010` (10/10) with the drawer
carrying the utensils under native stow welds until measured grasp/lift
validation. The compact per-seed report is also checked in at
`../../public/evidence/mujoco-policy-eval.json` for the browser judge path;
the full trace remains reproducible by supplying an output path under
`results/`. The result is not a challenge compliance claim.

## Teach, retry, reset, remember

```powershell
uv run --project sim/mujoco python -m fortifiers_mujoco.apprenticeship
```

This records a bounded hand-off correction in `results/dinner-skill-memory.json`,
retries the same policy, resets into a new seed, and verifies that the persisted
rule is used again.

## Bridge and task graph

The safe process bridge can be started with:

```powershell
uv run --project sim/mujoco python -m fortifiers_mujoco.bridge_server
```

It accepts only JSON commands (`reset`, `observe`, `step`, `policy_step`,
`policy_run`, `task_plan`, and `close`) over stdin/stdout. The task graph is
available independently through `task_plan` and includes a required two-arm
hand-off. Task-level actions now return live task state, including held
objects, verified placements, and the hand-off result. `policy_step` and
`policy_run` exercise the same closed-loop policy through the process boundary.

## OpenVINO benchmark

The compact checkpoint can be exported and evaluated as an OpenVINO IR model:

```powershell
uv sync --project sim/mujoco --extra edge --extra vla
uv run --project sim/mujoco --extra edge --extra vla fortifiers-mujoco-export-imitation-openvino results/imitation-policy.pt --output results/imitation-policy.xml
uv run --project sim/mujoco --extra edge --extra vla fortifiers-mujoco-eval-openvino results/imitation-policy.xml --episodes 10 --device CPU --output results/openvino-evaluation.json
uv run --project sim/mujoco --extra edge --extra vla fortifiers-mujoco-benchmark-openvino results/imitation-policy.xml --device CPU --output results/openvino-benchmark.json
```

The benchmark reports device, input precision, latency percentiles, and
throughput. It remains a separate model benchmark: task success is only
meaningful when the same real checkpoint is evaluated through
`fortifiers-mujoco-eval-openvino` on the same target device. The checked-in
CPU run measures 2.39 ms mean / 3.18 ms p95 / 418 FPS for inference-only
execution; the matching task smoke remains a separate `0/1` report. Browser
rendering and the staging collector do not count as OpenVINO or hardware
evidence.
